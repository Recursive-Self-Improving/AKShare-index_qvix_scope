# Daily GitHub refresh: independent proposal A

## Scope and evidence

Research-only proposal for AC17–21 in `docs/goals/sentiment-index-history.md:198–226`; no source acquisition, implementation, ledger mutation, deployment or push was performed. The active product is eight Sina index feeds and seven matched QVIX feeds, not the superseded news-sentiment series. `README.md` documents the existing v4 whole-snapshot, quality, provenance and offline-report contracts.

I requested LSP symbols for `app/fetch.py` and `app/core.py`; the LSP device returned **“No language server found for this action”** for both. The following inspection therefore uses direct source reads and the installed pinned wrapper's `inspect.getsource`, not guessed call relationships. Offline command:

```sh
uv run python -c 'import inspect,akshare as a, akshare.index.index_option_qvix as q; print(inspect.getsource(a.index_zh_daily_sina)); print(inspect.getsource(a.index_option_50etf_qvix)); print(inspect.getsource(getattr(q,"__get_optbbs_daily")))'
```

It shows `index_zh_daily_sina(symbol)` has no start/end argument and requests the full instrument endpoint; `index_option_50etf_qvix()` slices columns from the cached `__get_optbbs_daily()`, which downloads `http://1.optbbs.com/d/csv/d/k.csv` without date parameters. `app/core.py:20–28` identifies all seven wrappers and the same shared URL. This proves the pinned wrappers do not offer a windowed acquisition API; it does **not** prove no other provider API exists. The wrappers' own source, not a network probe, establishes this boundary.

## Actual behavior and consequences

* `app.fetch.worker` calls `ak.index_zh_daily_sina(symbol=feed)` before `core.decode` and `selected(..., start, end)` (`app/fetch.py:81–102`). The entire raw body is validated/decoded, then only inclusive-window rows are written to `observations.csv`. `core.histories` loads that CSV directly for the charts (`app/core.py:123–124,145–150`). Thus `--start` 30 days ago reduces the **chart**, not the provider transfer. There is no merge with the previous CSV.
* `fetch.group_worker` performs seven real wrapper calls against one cached shared load, persists each member before the next, and records full-raw QVIX quality while `core.qvix_artifacts` selects trace rows by window (`app/fetch.py:115–182`, `app/core.py:259–362`). A 30-day window similarly removes earlier QVIX trace data even though the whole shared file is fetched. Comparator calendars use the bound index snapshot's full raw body (`core.comparator_history`), not its selected CSV.
* `fetch.state_after` replaces the complete feed snapshot on **success or partial**, including a genuine fresh all-blank/no-close QVIX snapshot; only fatal failure uses that feed's own prior snapshot and marks it stale (`app/fetch.py:185–188`). `fetch.fetch` processes eight index subprocesses and one group subprocess, each with a 45-second wall limit, constructs a full v4 manifest and calls `promote` even when required feeds are partial/fatal. `fetch` returns 1 for *any* non-success (`app/fetch.py:236–280`); `README.md` records that all seven actual QVIX feeds were fresh partial. Exit 1 is therefore expected and must not itself skip charting, nor be silently converted to a successful workflow.
* `fetch.promote` validates the manifest and atomically writes its immutable run manifest and `latest.json`; it does **not** validate the report or preserve the public repository atomically with it (`app/fetch.py:224–233`). `app.verify.validate_snapshot` independently replays raw/wrapper and quality, checks origins, hashes and times, and re-derives each selected CSV; `verify` compares manifest, embedded trace arrays and visible disclosures (`app/verify.py:413–512,515–578`). This proves internal consistency, not completeness of a provider's later response, source authenticity, browser interaction or license rights.
* `fetch.main` defaults `--end` to local `date.today()` (`app/fetch.py:283–297`). A scheduler cannot rely on that default or local timezone. Raw responses may contain current/future-dated rows even when selected output excludes them; keeping exact raw provenance is intentional, but the selected manifest/CSVs/report must satisfy the cutoff. A stale prior snapshot may have been acquired with a later window; its own selected rows require an explicit cutoff check too.
* `capture_http` captures HTTP-decompressed response bodies and rejects multiple captures only **after** the request; `requests.get` follows redirects by default (`app/fetch.py:40–78`). Existing verification rejects redirected captures, but that does not prevent network access to the redirect target. An automation implementation should disable redirects at request time and test this security change separately; validation is not an egress control. QVIX's HTTP transport is unauthenticated; offline hashing cannot authenticate it.

## Decision: full-source snapshots, with a loss guard

Run the existing full-source acquisition every day with `--start 2000-01-01` and a UTC yesterday inclusive `--end`. This matches the existing whole-snapshot/revision policy, keeps full history in the chart, sees revisions older than 30 days, and costs the same source requests as a rolling window. The request is at most nine serialized worker budgets (8 × 45 s + 45 s), plus setup and offline verification; a job timeout must also cover Python setup, plotting, replay, artifact upload and Git operations.

A rolling-30-day **merge** would be a new data model, not a scheduler flag: it would need immutable source-by-date revision selection, retractions/conflicts, raw-ordinal and group identity provenance per row, full and selected quality recomputation, comparator binding, stale/fatal/blank handling, and independent replay of the merged revision set. It also cannot detect corrections outside the overlap and does not save downloads with these wrappers. Reject it for this goal. Retaining raw bodies alone while pointing the chart at a short CSV is likewise not historical preservation.

Full replacement alone is not safe against a valid but truncated provider response. Add an explicit independently tested **pre-publication loss guard** comparing the previously verified active snapshot with the candidate, per feed, for the intersection of their selected windows up to the new cutoff. For indices compare the set of dated observations decoded from the respective immutable sources; for QVIX compare per-feed nonblank source-date sets from replayed quality evidence, not shared CSV dates or merely the first/last dates/count. Detect missing dates anywhere, not just shrinkage of endpoints, and report feed, lost dates/count and both origin references. Distinguish an intentionally missing feed/no previous baseline from an empty set. Compare stale snapshots too, and verify both source artifacts first. Date-set equality does not prove unchanged values: revisions are allowed and their raw evidence remains immutable. This conservative policy may block a legitimate provider retraction: leave the prior public state intact, report the loss, and require an explicit reviewed recovery/backfill decision; do not silently stitch prior rows or claim source completeness. A fresh QVIX blank/error/conflict snapshot still follows the existing partial-replacement rule when no previously nonblank source dates disappeared; if dates disappear, publication is blocked as potential truncation rather than reclassified as a successful stale feed. The guard is a publication safety decision, not a rewrite of immutable acquisition results.

Run the guard and cutoff checks against the whole candidate manifest before publishing **any** feed. In particular, a stale prior selection that contains the current UTC day cannot be published merely because it verifies; stop and preserve the old public commit until a safe full-history candidate can be built. A previous snapshot with an unusually shorter selected window is not evidence of older available dates; flag the baseline condition in diagnostics rather than claiming complete historical coverage. A deliberate source deletion, invalid old evidence, or missing baseline requires explicit intervention, not inferred history.

## Firm implementation plan for independent review

1. Add a repository-owned Actions workflow with `schedule: cron: '5 0 * * *'` and `workflow_dispatch`, `permissions: contents: write` only, branch-scoped concurrency with `cancel-in-progress: false`, and a bounded job timeout such as 30 minutes. Run only on the intended publication branch, not arbitrary dispatch refs. GitHub cron is UTC and scheduled runs may be delayed or missed; concurrency is not a durable job queue (a pending run can be replaced). Manual dispatch is the recovery route. Document default-branch scheduling and branch protection/write-token prerequisites. GitHub references: [events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
2. Check out the intended branch and commit baseline; set up pinned Python 3.14 and `uv`, then `uv sync --frozen`. Compute one `end` at job start using an explicitly UTC-aware datetime minus one calendar day, pass it once to fetch, and record it in diagnostics. Do not compute a presumed last trading day: weekends and exchange holidays simply produce no invented dates. A delayed run uses actual job-start UTC date, documented as such. Ensure all selected report dates are `<= end`, including stale feeds, and check the manifest's intended full start.
3. Work in an isolated staging copy containing the existing complete tracked data and prior manifest; never mutate the checkout's publication candidates until all checks pass. Capture fetch exit code without `set -e` discarding expected partial results. Accept only explicit 0/1 classifications and valid complete candidate manifest; unexpected exceptions, missing results, corrupt baseline, failed manifest promotion, cutoff violation, loss guard failure or render/verification failure block publication. Preserve old checkout/public commit on all such paths. Keep raw immutable run files and previous-manifest references; do not delete older artifacts or rewrite them.
4. Render staging with `uv run python -m app.chart --input <stage-data> --output <stage-index.html>` then independently run `uv run python -m app.verify --input <stage-data> --report <stage-index.html>`, plus the baseline/candidate loss and date checks. These checks must examine actual feed snapshots/CSV/report dates, not only the top-level manifest window. A verified partial or fatal-with-prior-stale candidate may publish **only** if all loss/cutoff checks pass and visible disclosures remain truthful. A first-run fatal with no prior snapshot must not publish an empty feed in place of previously existing history; when no baseline ever existed, require all required feeds to have usable snapshots. Existing `verify` alone does not enforce these automation policies.
5. After checks, copy the exact verified new immutable artifacts, `latest.json`, and root `index.html` into the checkout, stage only intended paths, and commit them together. Run a staged-tree consistency check or verify the copied tree before committing; the commit is the atomic public unit. Do not use `git add -A`, alter historical files, force-push, expose tokens in command lines/logs, or push a candidate when verification fails. Use the short-lived Actions `GITHUB_TOKEN` with minimal permissions and checkout credential handling, not a personal token. Normal fast-forward push to the checked-out branch must fail safely on an intervening update; do not reset, overwrite, or force. A no-change case must not manufacture a misleading commit. Generated immutable runs normally make a successful acquisition a change.
6. Upload bounded diagnostic logs and the run's failure evidence as Actions artifacts even on failure, with retention limits and no secrets; summarize per-feed attempt/status, previous/candidate origin, UTC cutoff, loss checks, verification and commit/push result. After a safe partial/stale publication, explicitly fail the job or emit a documented equivalent prominent failure signal: recommendation is commit/push first, then exit nonzero, so GitHub's normal failure notifications remain available and historical provider defects are not called clean. A push or artifact failure must not be labeled successful. A failed push leaves only an unpushed runner commit; the remote remains unchanged. GitHub's default token-generated pushes generally do not trigger a branch-based Pages build; explicitly configure Pages via an appropriate supported Actions deployment workflow or document that publication requires a separately authorized Pages trigger. Do not assume a successful Git push deployed the site. See [triggering a workflow from a workflow](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) and [Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages). No external deployment or push during implementation.
7. Update README with permissions/setup, UTC cutoff and delayed schedule, first-run/baseline requirements, fresh partial versus stale/fatal and alert semantics, failed push/branch protection, manual recovery and full backfill, growth of immutable raw/CSV/HTML git history, provider rate/HTTP/authenticity and redistribution limits. Public branch publication exposes raw and derived data; verify license/authorization before enabling. The current source warnings are not solved by automation.

Assert actual committed report/manifest, logs and exit status rather than mocked call counts alone.

Index and all seven QVIX traces retain historical dates. A 30-day start fixture demonstrates why short-window output is rejected.

6. Malformed body, interrupted group after some durable siblings, unverified immutable timestamp/hash, bad HTML/disclosure, guard failure, missing artifact, timeout and chart failure never publish an invalid tree; logs/artifacts identify failure and recoverable siblings. 7. A competing branch update makes the normal push fail with no force; public branch stays at the competing commit, failure is visible. Test branch restrictions, minimal token permissions and no secrets in diagnostics. A verified commit contains matching `index.html`, `latest.json`, immutable origins and all referenced artifacts. Confirm that local tests cannot establish hosted schedule firing, hosted permission configuration, provider authenticity, external notification delivery or Pages deployment.

## Residual risks

Git history and raw captures grow every day, and Sina warns that heavy crawling may trigger IP blocking; eight full-index requests plus one shared QVIX request run each day, without unbounded retries. GitHub availability, schedule timing, branch protection, default-token behavior and Pages setup are external. Existing quality checks are relative to observed comparator history, not an official calendar; a provider losing the same dates in both sources can evade a same-run relative-gap check, hence the cross-run guard. The guard itself cannot prove coverage before the retained baseline or detect economic misstatements. Raw data and the generated HTML may be subject to redistribution restrictions.
